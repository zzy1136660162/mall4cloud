# Fantastic Admin 业务页面 UI 对齐与富文本接入

## 适用场景

- Vue 3 + Fantastic Admin 项目中的业务页仍直接堆叠 Element Plus 表单、表格，视觉层级与框架示例不一致。
- 后端返回 HTML 字符串，但编辑页仍使用 textarea，导致用户看到源码而不是可视化内容。

## 不适用场景

- 需要重构接口、字段、权限、路由或业务校验的需求。
- 只读详情展示且不需要编辑 HTML 的页面。

## 前置条件

- 确认目标应用已经提供 `FaPageHeader`、`FaPageMain`、`FaSearchBar`。
- 确认 TinyMCE 包、语言包和皮肤资源已经安装；优先复用同一应用中的 TinyMCE 示例配置。
- 先记录工作区已有改动，后续仅审查目标路径，避免覆盖用户文件。

## 推荐工具顺序

1. `rg` 定位目标视图、框架示例和现有富文本依赖。
2. `git status` 记录已有改动边界。
3. `apply_patch` 完成目标视图与独立富文本组件修改。
4. 运行结构契约检查、目标类型诊断、 ESLint、Stylelint、生产构建。
5. 在已有登录态的浏览器中做只读页面核对；无法接管登录态时明确报告限制，不读取或复制会话存储。

## 标准流程

1. 对照框架 example，确认页面缺少的容器组件和间距规则。
2. 保留查询对象、API 调用、路由、分页和提交函数，只替换模板层次与样式。
3. 将搜索区放入 `FaSearchBar`，表格放入 `FaPageMain`，补齐加载、空态、刷新、响应式和键盘查询交互。
4. 新建 TinyMCE `v-model` 包装组件，启用本地语言/皮肤、明暗主题、常用格式、图片、链接、表格、预览和源码模式。
5. 仅把详情字段的 textarea 替换为富文本组件，继续使用原字段和原提交对象。
6. 对目标文件执行类型诊断与样式检查，再运行完整生产构建。
7. 用 `git diff --check` 和目标路径状态确认没有越界修改。

## 关键校验点

- 原有 HTML 在编辑器 iframe 中渲染，而不是作为文本显示。
- 富文本组件仍输出 HTML 字符串，不改变后端字段协议。
- 搜索、重置、刷新、分页、编辑和删除入口仍指向原函数。
- TinyMCE 的语言包、明暗皮肤在最终 `dist` 中存在。
- 全量检查若包含历史错误，应单独输出目标文件诊断，不能把历史问题误报为本次回归。

## 常见失败与处理

| 现象 | 原因 | 处理 |
|---|---|---|
| 富文本仍显示 HTML 源码 | 详情字段仍绑定 textarea | 使用 TinyMCE `v-model` 直接绑定原详情字段 |
| 编辑器无样式或中文失效 | 静态资源路径缺失 | 复用应用 `public/tinymce` 下的语言包与皮肤路径 |
| 全量类型检查失败 | 仓库已有类型债务 | 过滤目标文件诊断，同时保留完整退出码并如实报告 |
| 无头浏览器跳登录 | 新上下文没有登录态 | 优先使用已有登录标签；无法安全接管时停止，不复制令牌或会话数据 |
| 页面样式检查失败 | CSS 属性顺序与项目规范不一致 | 仅对目标文件运行 Stylelint `--fix` 后再次验证 |

## 安全边界

- 不读取浏览器 cookie、localStorage、密码或令牌。
- 不点击保存、删除等有业务副作用的操作进行 UI 验证。
- 不修改框架内置组件；只在业务应用层组合使用。
- 不自动提交、推送或清理用户工作区。

## 可复用提示词

请按 Fantastic Admin 业务页面 UI 对齐与富文本接入流程执行：以 `<reference-app>` 为视觉基准优化 `<target-view>`，保持接口、字段和业务流程不变；将 `<html-field>` 接入已有 TinyMCE 能力。完成后输出目标文件、构建结果、目标类型诊断、浏览器验证情况、既有失败项与修改边界。
